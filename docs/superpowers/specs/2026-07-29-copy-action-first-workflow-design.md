# 正文工作台动作优先工作流

## 问题

当前正文页把任务启动、候选审核、历史消息和自由修改堆在同一个 Project Agent 对话框中。用户需要输入“开始做”才能生成正文，历史澄清消息会干扰当前任务，候选与正式文稿的边界也不直观。

## 目标

正文页以文稿为中心。用户进入空正文时，唯一主操作是“生成正文”；生成后的内容始终先作为候选，用户在候选预览中明确采用后才写入正式文稿。已有正文时，右侧只提供可理解的修改动作和一条可选补充要求。

## 交互设计

1. 空正文：显示“生成正文”主按钮和可选“先生成大纲”次级操作，不显示聊天历史或自由对话框。
2. 生成：主按钮使用已保存的写作策略、目标平台、已采用研究结果和用户资料，直接进入执行队列，不再展示“确认调用”中间步骤。
3. 候选：任务完成后自动打开候选预览。预览只提供采用、废弃和关闭；正式编辑区在采用前保持不变。
4. 已有正文：显示润色、扩写、压缩、重构等明确动作；用户可在单个“补充要求（可选）”输入框补充条件。选中文本时主动作变为“修改选中内容”。
5. 状态：右侧只显示当前运行、最近候选和必要错误。完整历史从正文主路径移除，避免旧的澄清消息干扰当前任务。

## 质量与数据边界

- 生成请求必须继承项目标题、核心观点、写作策略、平台规则和已采用研究结果。
- 候选不得自动覆盖正式文稿。
- 已确认研究事实与待核验项必须在候选预览中可见，正文生成不得将待核验项叙述为已确认事实。
- 生成提示词必须锁定项目主题，禁止把不相干的研究结论扩写为文章主线。

## 验收

- 空白正文无需输入文本，点击一次“生成正文”即可开始任务。
- 界面没有“自由对话”“发送”“确认调用”作为正文主路径。
- 生成完成自动进入候选审核；采用前正式文稿不变。
- 现有正文的修改动作不依赖自然语言关键词识别。
- 桌面端右侧仅有一个可选补充输入框，移动端单列可用。
